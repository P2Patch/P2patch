# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`P2Patch` is an automated security-remediation pipeline that drives Claude Code agents to **exploit → patch → verify** a security vulnerability, each agent running inside a project-specific Docker container. A FastAPI + React web UI ("P2Patch Lab", under `dashboard/`) sits on top for browsing, evaluating, launching, and comparing runs. See `README.md` and `dashboard/README.md` for the user-facing docs.

## Commands

The pipeline package (`security_pipeline/`) is **pure Python stdlib — no third-party deps** (`requirements.txt` is empty by design). There is no installed console script; the `security-pipeline` command shown in the README is invoked as a module:

```bash
python -m security_pipeline run --alert path/to/alert.json
python -m security_pipeline run --cve CVE-2022-26884
python -m security_pipeline run --all --limit 10 --profile baseline_eval
python -m security_pipeline run --alert alert.json --dry-run   # context/state only; no Docker/Claude
# Retry budgets (default 3 each; 1 == old one-shot gates that reject on first failure):
python -m security_pipeline run --alert a.json --max-correction-attempts 3 --max-exploit-attempts 3
# Throughput (see "Run speed" below):
python -m security_pipeline run --all --jobs 4                 # 4 alerts concurrently (0 = auto from Docker memory)
python -m security_pipeline fetch                              # clone project sources for alerts

# fixPOVs (curated real exploits certified against the official fix; a non-gating eval metric):
python -m security_pipeline fixpov list-projects                # local sources available to author POVs for
python -m security_pipeline fixpov status                       # per-project POV coverage / certification
python -m security_pipeline fixpov validate --project <slug>    # certify: reproduce on unpatched, blocked by official fix
python -m security_pipeline fixpov replay --project <slug>      # re-score existing patched runs (reconstructs each from buggy_commit_id + its patch)
python -m security_pipeline fixpov replay --project <slug> --from-worktree   # score the runs' preserved worktrees instead
python -m security_pipeline run --alert a.json --no-fix-pov-eval       # skip the fixPOV eval stage

# Residual-gap POVs (exploits the OFFICIAL fix leaves open; scores whether a patch beat upstream):
python -m security_pipeline respov status                        # per-project residual-POV certification
python -m security_pipeline respov validate --project <slug>     # certify: reproduces on unpatched AND still after the official fix
python -m security_pipeline respov replay --project <slug>       # re-score existing patched runs against the residual POVs
python -m security_pipeline run --alert a.json --no-residual-eval # skip the residual eval stage

# Residual-gap AUDIT (is the gap real / still open upstream? -- analysis, not scoring):
python -m security_pipeline respov reverify --project <slug>             # re-run the POVs independently, record OUTSIDE the manifest
python -m security_pipeline respov reverify --project <slug> --at <ref>  # + the falsifiability control: must be BLOCKED on the later tree
python3 benchmark/residual_povs/triage/sweep_upstream.py                           # refresh upstream evidence for every suite -> residual_povs/TRIAGE.json
python3 benchmark/residual_povs/triage/add_verdict.py --slug <slug> --pov <id> --status fixed-later ...   # record a human verdict

# Retrofitting gates onto finished runs (assess-only; never re-patches):
python -m security_pipeline retrofit --dry-run                    # list eligible runs and exit
python -m security_pipeline retrofit                              # verifier over every accepted `baseline` run
python -m security_pipeline retrofit --project <slug>             # one project's runs
python -m security_pipeline retrofit --gates regression           # non-default gate (not a baseline stage)
python -m security_pipeline retrofit --profile any --force        # re-assess regardless of profile/prior result
```

Tests (stdlib `unittest`, no runner dep):

```bash
python -m unittest discover -s tests            # all tests
python -m unittest tests.test_security_pipeline # pipeline unit tests
python -m unittest tests.test_dashboard_hardening
python -m unittest tests.test_security_pipeline.MetadataTests.test_resolves_alert_to_project_and_dockerfile  # single test
```

Dashboard:

```bash
./dashboard/dev.sh          # build frontend + serve everything on http://localhost:8000
# hot-reload dev instead:
cd dashboard/backend && uvicorn app:app --reload --port 8000   # API on :8000
cd dashboard/frontend && npm run dev                            # UI on :5173, proxies /api -> :8000
```

The dashboard backend has its own deps (`dashboard/backend/requirements.txt`: fastapi, uvicorn, etc.); the pipeline itself does not.

## Architecture

### Stage-based pipeline orchestrator

The pipeline is a linear sequence of discrete **stages**, not a hardcoded flow. The design lets you define new experiment arms (ablations) declaratively:

- `security_pipeline/stages.py` is the heart of the system. `STAGE_REGISTRY` maps stage names → `Stage` subclasses (`worktree`, `docker_build`, `exploiter`, `patcher`, `pov_after`, `converge`, `harden`, `regression`, `verifier`, `fix_pov_eval`, `residual_eval`). Each `Stage` declares `requires`/`produces`, and `resolve_experiment()` validates that a chosen stage list is runnable (every `requires` is produced by an earlier stage).
- **Self-correction — a failing gate goes back to the agent that owns it, it is not a verdict.** `PatchCorrectionLoop.converge(ctx, predicates, stage=...)` drives the patcher to a fix-point over a list of `Predicate`s (`pov_blocked_predicate`, `regressions_pass_predicate`); **all** predicates are re-checked after each patch — POV first, so a regression fix can't silently re-open the vuln — up to `--max-correction-attempts` (`RunOptions.max_correction_attempts`, default 3; **1 restores the old one-shot reject-on-first-failure gates**). Every objective patch gate runs through it: `converge` (POV-after + regressions, used by `full`/`baseline_eval`/`no_verifier`), the standalone `pov_after` and `regression` stages (`hardening`), and each hardening round's post-patch checks (variant blocked + original POV still blocked). The failing check is fed back verbatim (`render_correction_patcher_input`); the `stage=` tag names the gate in the `correction` steps and in the retry's own agent-IO folder (`patcher_correction_<gate>_a<N>`, bare `patcher_correction_a<N>` for `converge`). Two guards in `_repatch`: the POV tree must come out of the patcher run as it went in (see **POV integrity guard** below), and the regression command set may only grow (`_merge_regression_commands`, so a correcting patcher can't drop the tests it's judged by). Command/step names are unchanged (`pov_after_patch`, `regression_N`, `patch_and_regression`) so the dashboard/analysis keep working — a retried gate simply records that command more than once, last-wins (one gate line in `dashboard/backend/runs.py:rail_stages` maps `converge` → both rail items).
- **Exploiter retries (`ExploiterStage`):** a POV that does not reproduce on the *unpatched* code (or output that fails `validate_exploiter_output`) is fed back to the exploiter (`render_exploiter_retry_input`) up to `--max-exploit-attempts` (`RunOptions.max_exploit_attempts`, default 3; 1 = the old one-shot gate). Retries get their own agent-IO folder (`exploiter_retry_a<N>`) and docker log (`pov_before_patch_a<N>`) so each attempt is inspectable. A crashed/refused agent is **not** retried — that's infra/policy, not something the exploiter can fix. `dashboard/backend/runs.py:_retry_summary` folds both loops into the run payload's `retries` field (rendered by `RetriesPanel`), and the live monitor's `_RETRY_AGENT_PREFIX` keeps the rail showing the retrying agent instead of looking stalled.
- **The regression gate is a baseline diff, not an exit code (`regression_diff.py`).** A failing regression command is only a *genuine* regression if a test that **passed on the pristine pre-patch baseline** now fails. Every other reason these commands exit non-zero is scaffold: the pipeline's own POV, compiled into the project's test tree, is re-run by `mvn test` and its vuln-present assertion fails once the patch works; a test that only fails because the container runs as root; a pre-existing/flaky failure; an unrunnable command the agent picked (bad `-Dtest` filter, "No tests were executed"). All of those fail on the baseline too. So when a command fails, `regressions_pass_predicate` exports the run repo's `HEAD` (untouched source — the patch and the POV are uncommitted/untracked, which is exactly why the injected POV test shows up as *absent from the baseline* rather than as a regression) to `run_dir/baseline_checkout`, replays the same command there via `DockerRunner.for_checkout`, and compares JUnit XML (`parse_junit_reports`, mtime-filtered so a previous command's surefire output is not inherited). Only genuine failures are fed back to the patcher; scaffold ones pass the gate and are recorded as `regression_triage`/`scaffold` steps. Every path that cannot make the comparison — no baseline export, a replay timeout — falls back to "genuine", so a broken replay can never launder a real regression into a pass.
- **POV integrity guard (`StageContext.baseline_pov` / `enforce_pov_integrity`).** The patcher must not touch its own witness, so the POV tree is snapshotted **immediately before every patcher invocation** (`PatcherStage`, each hardening round's patcher, and `_repatch`) and restored from that snapshot afterwards; anything it changed is recorded as a `pov_guard`/`restored` step naming the paths. Two things this design is deliberately *not*: (a) it is **not run-wide** — a single baseline blamed the next patcher for POV variants the *exploiter* had legitimately added in a hardening round that exited via `stable` (which never re-baselined), and (b) it **does not hash build output** (`POV_ARTIFACT_DIRS` + `POV_ARTIFACT_SUFFIXES` in `workspace.py`) — re-running the POV to self-verify is expected and encouraged of the patcher, and `javac Pov.java` with no `-d` drops a `.class` right in the POV root. Both mis-readings rejected correct patches (4 of the first 9 `hardening` runs). It also **restores rather than rejects**: the POV is text we hold a snapshot of, so a patcher that neutered it simply meets the original POV at the next gate and gets sent back with a real failure, instead of a run several hardening rounds deep being discarded. Finally, it **never follows a symlink**: a link in the POV tree is snapshotted and restored by its *target string*, never by the bytes it points at. Dereferencing meant `pov/alias.java -> ../../src/Main.java` got the product file read into the snapshot and then written back over it — silently reverting the patcher's own fix, after which the run could not pass the POV-after gate it was being sent back to fix.
- **Product-source guard (`StageContext.baseline_sources` / `enforce_source_integrity`).** The mirror image of the POV guard, and the reason it exists: in a hardening round the exploiter runs **in the already-patched worktree**, so anything it edits outside `.security-pipeline/` rides into the final diff that the verifier and the offline judges score — and the `status != pov_created` early exit declares that patch `stable` without ever looking. The prompt already says "do not patch product code or normal tests"; this enforces it around **every** exploiter invocation (initial, retries, hardening rounds). Only what `git status` reports as changed is captured, so the cost is the size of the patch surface, not the repo: a file already modified is restored to its recorded bytes, a file that was pristine is `git checkout`ed back to HEAD, and a file the run created is deleted. Ignored build output and untracked files under a build-output directory are left alone (a project with no `target/` ignore rule would otherwise have its incremental build thrown away). Restores rather than rejects, and records a `source_guard`/`restored` step naming the paths.
- **fixPOV evaluation (`fix_pov_eval` stage):** every profile ends in `fix_pov_eval`, a **non-gating** step (`security_pipeline/fix_pov.py` + `FixPovEvalStage`). It replays a project's *curated* fixPOVs — checked in under `benchmark/fix_povs/<project_slug>/`, derived from the CVE's advisory + fix commit and certified once to reproduce-on-unpatched / blocked-by-official-fix — against the pipeline-patched code, to **measure** real-exploit coverage (score = blocked/(blocked+reproduced), written to `security_pipeline_runs/<run>/fix_pov/results.json`). It NEVER rejects a run: a POV that still reproduces, a missing/broken manifest, or a container error are recorded, not raised. It runs LAST (after the verifier) and stages POVs under `.security-pipeline/gtpov/` which it removes before returning, so no agent ever sees the fixPOV files/official fix and nothing leaks into a persisted diff. Same POV exit-code convention as the exploiter (exit 0 == reproduced), plus a reserved **exit 2 == harness/build error** that is classified `errored` and excluded from the score. Three things keep the score from crediting a patch for a broken run rather than a real fix, because "non-zero == blocked" is a dangerously forgiving default: (a) **staging failures are checked by the harness, not self-reported** — if a `setup_commands` entry or the `build_command` exits non-zero, every POV is recorded `errored` and the score is `null`, since a POV exiting 1 because no class file was ever produced is not a blocked exploit (a `build_command` of `false` used to yield `score: 1.0`); (b) **only a certified POV can score** — `evaluate_manifest` checks `validation.certified` *and* a `content_hash` fingerprint over the POV sources, command, exit-code contract, official fix, and revision, so editing a POV after certifying it invalidates it instead of silently inheriting the badge (`fixpov validate` opts out, being what creates certifications; pre-fingerprint manifests still run and report as `unsealed`). **That staging path is frozen at its legacy `gtpov` name**: certified manifest commands embed it (`bash .security-pipeline/gtpov/run.sh`) and the command is part of the fingerprint, so renaming the directory would invalidate every `content_hash` in the repo; (c) POV harnesses **rethrow JVM `Error`s** rather than counting a `NoClassDefFoundError` as "the fix rejected the payload". `all_blocked` additionally requires every POV to have been *tried*. Author new POVs with `benchmark/fix_povs/GENERATING_POVS.md`; certify with `fixpov validate` (builds the project and runs POVs before/after applying `official_fix.patch`). POV ids are restricted to safe basenames — they name docker log files. The run-local `results.json` is de-identified (`redact_for_run_artifact` drops `cve_id`/`project_slug`) to match the rest of the run-artifact contract, since the dashboard maps a run back to its CVE through its own index. If POVs are authored later, `fixpov replay --project <slug>` refreshes all existing accepted patched runs without rerunning the pipeline. Drop the stage from new runs with `--no-fix-pov-eval` (see `EVALUATION_ONLY_STAGES`). The family was called "ground-truth POVs" before the paper renamed it: runs recorded on the server before the rename still carry a `ground_truth_eval` step and a `ground_truth/results.json`, and every reader (dashboard, replay, retrofit) falls back to those legacy names when the new ones are absent.
- **Residual-gap POV evaluation (`residual_eval` stage):** the mirror image of `fix_pov_eval`, and the last stage of every profile (`security_pipeline/residual.py` + `ResidualEvalStage`, POVs under `benchmark/residual_povs/<project_slug>/`). fixPOVs ask *"did the patch match the official fix?"*; this asks *"did it **beat** the official fix?"* — it replays exploits for paths the CVE's **official upstream fix does not close**. Those exist: the completeness audit (`benchmark/fix_povs/COMPLETENESS_CHECKLIST.md`) found the same `canonicalDest.startsWith(dir)`-without-a-trailing-separator bug in **six** projects' official fixes (a sibling dir sharing the destination's name prefix still escapes), plus antisamy's fix removing children from a live `NodeList` by index while iterating (a `<style>` tag with 3+ smuggled children still leaks an executable node past the "fixed" sanitizer). None of them could be a fixPOV: `fixpov validate` certifies by proving a POV is *blocked by* the official fix, and these reproduce against it by definition — the very property that makes them interesting. Three things define this stage:
  - **The certification oracle is inverted, not removed.** A residual POV is certified when it reproduces on the unpatched tree **and still reproduces** after `official_fix.patch` (`residual.certifies`, `respov validate`). Dropping the "after" check entirely was the obvious simplification and is wrong: it is the only thing separating a genuine residual gap from a harness broken such that it always exits 0 (which would mark every patch as leaving the gap open) and from a path upstream actually *does* close (which belongs in `benchmark/fix_povs/`, where it would score). `official_fix.patch` is therefore **mandatory** here, unlike for fixPOVs where it is optional.
  - **Scoring is a bonus, never a deficiency.** `blocked` = the patch closed a hole upstream left open (credit); `reproduced` = the patch has the same gap upstream does, which is the expected, neutral norm and **not** a failure — matching the official fix is exactly what the fixPOV score already rewards. So `score = blocked/(blocked+reproduced)` reads as "of the holes upstream left open, what fraction did this patch also close", and **a score of 0 is a perfectly good result**. The summary deliberately renames the fields (`hardened_beyond_fix` / `matches_official_fix`) and drops `all_blocked`, so no consumer renders a high `reproduced` count as red; the dashboard panel colours `reproduced` neutral for the same reason. Kept as a separate score rather than folded into the fixPOV one, which would conflate "as good as upstream" with "failed to fix".
  - **Same isolation contract as fixPOVs.** Non-gating (every exception is swallowed into an `errored` step — it can never turn an accepted patch into a rejection), runs dead last so no agent ever sees these files or the official fix, and stages under `.security-pipeline/respov/` — a *sibling* of `gtpov/`, so a run evaluating both families cannot have one clobber the other — removed before returning. Reuses `fix_pov.evaluate_manifest` (staging, session reuse, `build_command` fast path, staging-failure handling, exit-code classification) via `stage_parts`/`certification_fn` parameters rather than duplicating it. Author with `benchmark/residual_povs/GENERATING_RESIDUAL_POVS.md`; `--no-residual-eval` drops it, independently of `--no-fix-pov-eval` (each flag strips only its own stage). Like fixPOVs, `respov replay --project <slug>` re-scores existing accepted runs without rerunning the pipeline (same reconstruct-from-`buggy_commit_id`+`patch_only.diff` machinery — `fixpov replay` and `respov replay` share one driver, `_replay_eval`, parameterized by a `_ReplayFamily` descriptor; results land in `security_pipeline_runs/<run>/residual/results.json`, a sibling of `fix_pov/`).
- **The residual audit is a separate track from the residual *score* (`respov reverify`, `benchmark/residual_povs/TRIAGE.json`, dashboard "Residual audit").** Certification makes a residual POV a usable instrument; it does not make the gap a finding, and three things stop it from doing so. (a) `respov validate` **writes its verdict into the manifest it is certifying**, which is fine for scoring and wrong for an audit — so `reverify` re-executes the same POVs and writes to `benchmark/residual_povs/verification/<slug>.json`, a file no certifying code touches. (b) The residual oracle is **one-sided** (reproduce, reproduce), so `--at <ref>` runs the POVs against a tree where upstream is claimed to have closed the gap and requires `blocked` there; that is the negative control certification structurally cannot provide, and it is the only thing separating a real gap from a POV that exits 0 on every tree. (c) The certified "after" tree is `buggy + official_fix.patch`, which **never shipped** — `--at <release-tag>` scores a real one. Three rules the module encodes: `errored` is evidence for nothing (a POV authored for a 2018 tree usually will not compile against a 2025 one — measured: the per-CVE builder image pins an old Maven, so plexus-utils/plexus-archiver controls come back `inconclusive`, not `blocked`); the `--at` checkout is a **private clone**, never `benchmark/dataset/project-sources` (shared, `--depth 1`, and every run and certification reads it); a **short SHA can fail to check out** even when `gh api` resolves it, so pass a full SHA or a tag; and `--repo` exists because **one dataset row's `github_url` is not upstream at all** — zip4j points at `iris-sast/zip4j`, which is `fork=false, parent=null`, created 2025-06-30, and holds *decompiled sources-JAR* snapshots (its `59aeea59` is a 2025 commit titled "Add decompiled source for 1.3.3 (fixed)"), so no upstream commit or tag resolves in it and the row's "official fix commit" is synthetic even though its patch content is genuine 1.3.3 code. First executed result: antisamy's two residual POVs reproduce on unpatched and on the official fix, and go `blocked` at upstream's own follow-up commit `21c4061` — the control passes. `triage/sweep_upstream.py` collects the cheap half (are the official fix's own added lines still verbatim at upstream HEAD?) for all 40 suites, and its signal is a **lead, not a verdict**: cxf reads `fix_intact` because the 2016 fix's lines are untouched, yet upstream closed the residual gap in 2020 by *adding* an escape elsewhere in the same file.
- **Replay reconstructs the patched tree; it does not trust a leftover worktree (`_ReplayCheckout`).** `fixpov replay` exports the project's `buggy_commit_id`, applies the run's recorded `git/patch_only.diff`, and scores *that* — falling back to the run's preserved `worktree/` only when reconstruction is impossible (no diff, base commit absent from the shallow clone, patch does not apply), and recording which tree produced the number as `evaluation_mode` (`reconstructed` / `worktree`) in `results.json` and the `fix_pov_eval` step. Scoring the preserved worktree was the original design and it has two failure modes reconstruction does not: (a) `security_pipeline_runs/` is gitignored and can be GBs, so once worktrees are pruned those runs are permanently unscoreable — a commit id plus a diff is a few KB; (b) the base is whatever `benchmark/dataset/project-sources/<slug>` points at *today*, and several of those checkouts have drifted onto upstream `main`, where a POV certified against the vulnerable revision proves nothing. Measured on 31 real runs, 30 of their diffs apply cleanly to `buggy_commit_id`, and a full replay of a spark 2.7.1 run reproduced the worktree score POV-for-POV. Three things this deliberately does *not* do: it does **not** record the base commit in any run artifact (`buggy_commit_id` identifies the CVE — `DockerRunner` already redacts it from every docker log — and the base is re-derivable from the run's `finding_id` through `project_info.csv`, which is how the dashboard maps a run to its CVE); it does **not** re-export per run (one checkout is reused and `reset_checkout`ed between runs, which keeps ignored build output so only the first replay in a batch pays for a cold build — same reason the agents may not run `mvn clean`); and it does **not** `git clean -x`, for that same reason. `--from-worktree` restores the old behaviour.
- **A run's diff must stay appliable (`collect_git_diff`).** The untracked-file path passes `--binary --full-index`. Without them an untracked *binary* file — the `Pov.class` a patcher drops in the repo root when it re-runs the POV to check its own fix — was recorded as a contentless `Binary files ... differ` stanza, and `git apply` then rejected the **entire** patch (`cannot apply binary patch ... without full index line`), taking reconstruction-based replay down with it. Note this is about `git apply`-ability only; the diffs are still decoded with `errors="replace"` and are not byte-exact for non-UTF-8 files, which makes a corrupted patch fail loudly at apply time rather than reconstruct a wrong tree.
- **Retrofitting gates onto finished runs (`retrofit.py` + the `retrofit` CLI) is assess-only.** `baseline` gained the verifier after 40 runs had already been recorded without it; `retrofit` replays it (default `RETROFIT_GATES`; `regression` stays in `AVAILABLE_GATES` for `--gates`, since `hardening` has that stage) against such a run's **existing** patch so the old and new runs are comparable. It never re-patches, and that is the load-bearing constraint, not a shortcut: `PatchCorrectionLoop` sends a failing gate back to the patcher, which would rewrite `git/patch_only.diff` — and every fixPOV and residual score already recorded for that run was computed against the diff on disk, so they would silently become numbers about a patch that no longer exists. It therefore drives the gates through `stages.assess_predicates` (the read-only half of `converge`: check each predicate once, record the commands, return the first failure) and reuses `VerifierStage`, catching its `StageError` instead of obeying it. `status`/`reason` in `state.json` and `verdict.json` are untouched; the outcome lands in a `retrofit_gates` headline plus `run_dir/gates/results.json` (a sibling of `fix_pov/` and `residual/`). Five things worth knowing: (a) it scores a tree **reconstructed** from `buggy_commit_id` + the run's `patch_only.diff`, falling back to the preserved worktree, exactly like `fixpov replay` — and it hands the *pristine* half of that reconstruction to the regression gate as `baseline_checkout_path`, because a reconstructed checkout carries the patch in its working tree so the gate's usual `git archive HEAD` would export the patched code as the "baseline"; (b) a gate the run **already ran natively** is dropped from its target, so a retrofit can never overwrite a real verifier verdict (`--force` overrides); (c) a gate the retrofit itself **errored** on (agent crash, expired OAuth, container failure) is retried automatically — recording the attempt adds its stage to the run, and without subtracting `gates_errored` that run would look permanently gated by an assessment that never happened; (d) an errored gate is **not** a failed gate: only a real `rejected` verdict or a genuine regression counts against the patch; (e) writes are **merges**, not replacements — a retrofit covering only some gates keeps what an earlier one recorded, and the state purge removes prior entries by **identity** (the exact fragments recorded in the previous `results.json`) rather than by name prefix, since `verifier`/`regression_N` are not unique to this module and a prefix purge would delete a `full` run's own artifacts.
- **To add an experiment arm, add a row to the `PROFILES` dict** (and `PROFILE_PATCHER_EVIDENCE`) in `stages.py` — no orchestrator changes needed. The `--profile` flag selects the arm; `--stages a,b,c` overrides ad hoc.
- `security_pipeline/pipeline.py` (`SecurityPipeline.run_alert`) is the thin driver: load alert → resolve metadata → build a `StageContext` → run each stage in order, converting a `StageError` into a `rejected` verdict.

### Profiles (the core A/B knob)

The whole point is measuring whether exploitation helps the patcher. The distinguishing variable is `patcher_evidence` (`full` vs `alert_only`):
- `full` — exploiter builds a POV, patcher sees it, all objective gates run.
- `baseline` — alert-only patch: no exploiter and no POV, but the patch is still reviewed by the **verifier**, which needs no POV (`render_verifier_input` has an alert-only evidence mode). Judging a `baseline` patch by nothing while a `full` patch had to survive a reviewer made the arms differ in *gating* as well as in evidence; now only `patcher_evidence` does. Deliberately **no `regression` stage**: that gate exists to feed a broken test back to the patcher and this arm has no self-correction loop, so the verifier runs the project's tests itself and weighs the result in its review — same information, one container pass, no redundant gate. Still also judged offline (dashboard LLM judge).
- `baseline_eval` — same gates as `full`, but exploiter output is **withheld** from the patcher. This is the controlled comparison.
- `no_verifier` — `full` minus the LLM verifier gate.
- `hardening` — after the baseline patch fixes the original POV, iteratively loop exploiter (hunt a new bypass variant) ↔ patcher (strengthen the fix) up to `--max-rounds`, stopping early when no new bypass is found (`HardeningLoopStage`).

The skip-if-already-run check is **profile-aware** (keyed by a stable `finding_id` = sha256 of alert name + project slug + CVE), so you can run `baseline` over projects that already have a `full` run without `--rerun`.

### Run speed

`docker build` is **not** the bottleneck — the layer cache makes it a ~2s no-op after a project's first run. Wall time is dominated by agent turns (LLM latency), and within those, by repeated project builds. Two levers, both measured on a quiet machine (contention badly skews any timing here — measure when nothing else is running):

- **Run-level parallelism.** `run --jobs N` runs N alerts concurrently on a `ThreadPoolExecutor` (threads, not processes: `run_alert` only waits on `claude`/`docker` subprocesses). `SecurityPipeline` holds no per-run mutable state; run-directory allocation is claimed under a lock in `pipeline.claim_run_dir`. `--jobs 0` sizes from Docker's memory via `_auto_docker_jobs` (~3 GB per concurrent run, capped at 4) — the same helper `fixpov validate --jobs` uses, since both are limited by the same resource. The dashboard has its own independent concurrency queue in `live.py`, so `--jobs` only affects the CLI path.
- **No `clean` in agent builds.** Build output persists across commands in a worktree, so an agent's second and later builds are incremental — `mvn clean` throws that away. Measured on dolphinscheduler 2.0.5 (`mvn -B -DskipTests package`): 5:32 from scratch vs 3:31 incremental in the same tree. Both agent prompts forbid `clean`, and **`agent_guard.py` now enforces it** — see below.
- **Agent discipline is enforced, not requested (`security_pipeline/agent_guard.py`).** A profile of the first 30 runs (69 agent invocations, 7.7 h of agent wall time, 64% of it API latency) found the prompts were being ignored where it cost the most: 44 `mvn clean` invocations, 103 unscoped full-test-suite runs *on top of* the pipeline's own regression gate, and 18.5 min lost to backgrounding a build and then blocking on `tail -f`/`sleep` (one patcher spent 14 of its 27 min of tool time that way). The guard is a `PreToolUse` hook on `Bash`, wired in through a generated per-agent `--settings` file, that rejects `clean`, background Bash, `tail -f`, long `sleep`, and polling loops, feeding the reason back to the agent. Prompt rules stay in place so the agent knows the rule before it trips it. **It also blocks network egress** (`egress_reason`): `curl`/`wget`/`scp`/`ssh`/`nc`/`telnet` to any non-loopback host, `git clone|fetch|pull|ls-remote`, `pip`/`npm`/`go get`/`cargo` installs, and python `urllib`/`requests`/`urlopen`/`http.client` — because agents were using Bash to reach the internet and route around the `WebSearch`/`WebFetch` ban (see `DISALLOWED_TOOLS` below). Loopback (`localhost:PORT`, `127.0.0.1`, listen-mode `nc -l`) stays allowed so an HTTP-server POV can still drive itself. This guard is the *readable* layer (it gives the agent a reason instead of an opaque failure and also covers a command run on the host rather than in the container); the airtight layer is container network isolation (see next bullet).
- **Agent-facing containers are network-isolated (`docker_runner.py`, `P2PATCH_AGENT_NETWORK`).** A profile of all 432 runs found 21 where an agent `curl`ed the GitHub API / `raw.githubusercontent` / NVD / a fix-commit `.patch` / a source tarball / a search engine — reaching the advisory and the **official fix commit** the CVE-redaction and `WebSearch`/`WebFetch` ban exist to hide, which contaminates the fixPOV/residual POV scores derived from that same advisory. So the three agent-facing `docker run` argv builders (`command_args`, `_start_session`, and the `run_in_docker.sh` wrapper the agent drives directly — `docker exec` in a session inherits the run container's network, and `for_checkout` reuses `command_args`) now carry `--network none` by default. **`docker build` is deliberately untouched** — the image build legitimately fetches Maven/git during layer construction, and deps baked into the image at build time mean incremental agent builds run offline against the cached `~/.m2`. A project whose build genuinely must fetch at agent-time opts back in with `P2PATCH_AGENT_NETWORK` (a docker network name, or `bridge`/`default`/`host`; empty or `none` == isolated) — e.g. a named network fronted by an allowlist proxy that permits package registries but not GitHub/NVD. **The cutoff is scoped to containers an agent actually touches, and that scoping is load-bearing.** `DockerRunner(network=...)` defaults to the agent policy; `EVALUATION_NETWORK` (via `for_evaluation()`, used by the `fix_pov_eval`/`residual_eval` stages and by every offline driver that only runs curated POVs — `fixpov`/`respov` `validate` and `replay`) marks a runner **no agent ever touches**, and it stays connected (`P2PATCH_EVAL_NETWORK` overrides; default `bridge`). Isolating those containers protected nothing — the agents have exited and the stage has the official fix on disk anyway — while breaking the POV staging builds, which legitimately fetch: `mvn dependency:build-classpath` and `mvn install` pull plugins the project's own `package` never used (so they are absent from the image's warm `~/.m2`), and the coreutils harness clones gnulib. And the damage is silent-ish rather than loud: a staging failure correctly records **every** POV as `errored` with a `null` score, so four hardening runs came back with no fixPOV or residual number at all, looking like broken POVs. `for_checkout` deliberately **inherits** its parent's policy rather than taking the evaluation one — the regression gate replays an *agent-authored* command in that container, whose output is fed back to the patcher.
- **Prompt payloads are clipped (`clip_text` / `command_evidence` / `clip_diff` in `stages.py`).** A task input is re-sent on every turn and agents average ~35 turns, so payload size is paid for repeatedly. Observed median 51 KB, worst 117 KB — 70 KB of it one echoed patch diff, with failing-`mvn test` logs up to 46 KB elsewhere. Command logs are head+tail clipped and diffs capped, with the elision stated inline. **The alert is deliberately never clipped** — it defines the scope of a complete fix, so trimming it would change the task rather than the token bill.

**Rejected: seeding the worktree with the image's prebuilt `target/`.** Each Dockerfile builds the project inside the image, and the worktree bind-mount shadows that, so pre-copying the output looks like an easy win. It is not — measured cold vs seeded: commons-io 4.6s → 2.8s, antisamy 4.5s → 6.6s, dolphinscheduler 5:32 → 6:13. For a big multi-module build, `package` re-runs every plugin regardless of what is already compiled, and pushing GBs of artifacts through a macOS bind mount costs more than recompiling. It also carries a correctness hazard: the image is built from an upstream `git clone` at the Dockerfile's `GIT_COMMIT`, and 1 of 20 local `project-sources/` checkouts (zip4j) is at a *different* commit — seeding there injects classes that do not match the sources, and Maven silently trusts them. Don't retry this without a commit-equality guard and per-project evidence it helps.

### The benchmark data lives under `benchmark/`

The CVE corpus, the Dockerfiles and both curated POV families are checked into
this repository under `benchmark/`. It is a plain directory, not a submodule, so
a clone needs no extra step. Three things follow.

- **Never spell a benchmark path at the call site — go through `security_pipeline/paths.py`** (`dataset_dir`, `project_info_csv`, `dockerfiles_dir`, `project_source`, `fix_povs_dir`, `residual_povs_dir`). Moving the data is then one edit, and `require_benchmark()` can give one accurate error naming the directory that is missing instead of every caller reporting its own file as absent. `P2PATCH_BENCHMARK` relocates the checkout entirely, which is what a run host with the sources on another volume needs.
- **Resolve against `config.REPO_ROOT` at call time, not import time.** The dashboard exposes `config.fix_povs_dir()` / `residual_povs_dir()` / `dataset_dir()` as *functions* for exactly this reason: tests relocate the tree by patching `config.REPO_ROOT`, and a module-level constant silently ignores that — it keeps pointing at the real checkout while the test writes fixtures into a tmpdir, so a lookup can pass by reading the developer's own data. Four tests caught this during the split.
- **`benchmark/.gitignore` excludes `benchmark/dataset/project-sources/`** (a nested ignore file applies to its own subtree), and both it and the root `.gitattributes` set `* -text`: `project_info.csv` is CRLF and the zip4j/hutool `official_fix.patch` files must stay CRLF or `git apply` rejects them wholesale — worse, every `official_fix.patch` is hashed into its POV's certification `content_hash`, so a newline rewrite does not merely break an apply, it invalidates the certification and the suite silently stops scoring. A machine with `core.autocrlf=input` (a common default, and the one on this host) does exactly that on `git add`; it corrupted four files on the first attempt at this split and was caught by diffing blob hashes against the source repo.

Note `respov reverify` **writes** its audit under `benchmark/residual_povs/verification/`, so a reverify run shows up as ordinary modified files here.

### The AutoSec → P2Patch rename

The project was renamed; two consequences are not cosmetic.

- **Env knobs are `P2PATCH_*`, and the old `AUTOSEC_*` spelling still works** (`security_pipeline/env.py:get_env`, used by `docker_runner`, `zai`, `openrouter`, and the dashboard's analysis model override). Reading only the new name would silently unconfigure every host already set up — a run host that had opted its builds back onto the network via `AUTOSEC_AGENT_NETWORK` would go isolated again and start failing builds with no visible cause. The fallback is one-way (nothing writes the old name back) and an **explicitly empty** new value wins, because `P2PATCH_AGENT_NETWORK=""` means "isolated", a real choice rather than "unset".
- **Docker images are now `p2patch-<slug>:<dockerfile-hash>`** (`docker_runner.IMAGE_PREFIX`), so the first run of each project after the rename pays a **cold build** — the layer cache is keyed by image name and nothing matches the old `simpleautosec-` tag. Where the code *reads* images back rather than building them, both prefixes are matched (`LEGACY_IMAGE_PREFIX`; the dashboard's `_docker_image_for_run` passes two `--filter reference=` terms), since a host mid-migration may hold only the old images and that container just runs `find -delete`.

Deliberately **not** renamed, because they name things outside this repo: the OpenRouter preset slug `autosec-glm52-streamlake` (a real workspace-scoped preset — renaming the string breaks routing), the server paths `/root/autosec*` and the `ssh autosec` host alias, the `ceenaa/autosec` git remote, and the `simpleautosec-*` container names quoted as evidence in POV `NOTES.md` (those record what was actually run).

### Alert → project resolution

`security_pipeline/metadata.py` resolves an alert JSON to a project + Dockerfile via CSV lookups in `benchmark/dataset/` (`project_info.csv`, `build_info.csv`, `project-sources/`, `Dockerfiles/`). `benchmark/` holds the project metadata, per-project Dockerfiles, both POV families, and the (gitignored) `project-sources/` clones — **never build a path into it by hand, go through `security_pipeline/paths.py`** (see below); `finder_results_filtered/` holds the curated alert JSONs the pipeline runs against.

- **`buggy_commit_id` must be a full 40-char SHA.** `security_pipeline/fetch.py` (`python -m security_pipeline fetch [--project <slug>]`) does `git clone --depth 1` → `git fetch --depth 1 origin <id>` → `git checkout <id>`, and only a full SHA survives both steps. An **abbreviated** SHA fails the fetch outright (`couldn't find remote ref cc6a386` — you cannot fetch a short SHA). A **tag name** fetches fine but the fetch creates no local ref, so the checkout fails with `pathspec ... did not match`; a full SHA is immune because the object is local by then and a full SHA is directly checkout-able. Six C/C++ rows shipped with short SHAs or tag names and were unclonable until their cells were expanded to full SHAs (the tag rows to the tag's *peeled* commit, `refs/tags/X^{}`). Fix the data, not the fetcher: teaching the fetcher to fall back to `FETCH_HEAD` also works, but `FETCH_HEAD` can hold multiple lines and `checkout FETCH_HEAD` silently takes the first — a wrong-revision failure mode with no error, which is a bad trade for a benchmark whose whole premise is being on the vulnerable commit. Nine rows still have an *empty* `buggy_commit_id` and remain unclonable.
- **`project_info.csv` is CRLF.** Rewrite it with binary I/O; `Path.read_text()` translates `\r\n` → `\n` on read and a one-cell edit then rewrites all 228 lines (same newline-translation trap as diff capture, above).
- **Sharing a CVE id with another benchmark does not mean sharing a commit (`baselines/patch_source.base_plan`, `replay-patch --base-revision`).** Our C/C++ rows come from VulnLoc+ and San2Patch's from VulnLoc, which are the same 37 cases — so the join in `baselines/cases.json` is on `cve_id` and for 34 of them the two datasets do pin the same revision. The exceptions are not drift: **upstream sometimes fixed a CVE twice, and VulnLoc pins the bug at the *first, incomplete* fix while we pin it before any fix.** zziplib CVE-2017-5974 is ours at `3a4ffcdd` and theirs at `03de3be` (upstream's own "CVE-2017-5974 / CVE-2017-5976" commit, later completed by `9e8f867a`); CVE-2017-5975 is theirs at `33d6e9c` ("check file header magic / CVE-2017-5975", later completed by `64e745f`). Scoring such a patch on our tree fails in both available ways: `git apply` rejected the 5974 patch outright, and the 5975 patch applied by context and then **would not compile** — `memdisk.c:188: use of undeclared label 'error'`, a label the newer commit introduced — which the staging-failure guard correctly recorded as `errored` rather than as a blocked exploit. (libjpeg-turbo CVE-2017-15232 also differs, by 11 packaging commits that touch nothing relevant; it applied cleanly and its score was already sound.) So the base is **read from the benchmark, not assumed**, and a mismatched patch is reconstructed on its own commit. Two things make that safe: the shared `benchmark/dataset/project-sources` clone is **never fetched into** (`_clone_for_revision` makes a private clone under the replay dir — that checkout is what our own runs, every certification and every other baseline read, and a comparison harness must not deepen it), and **every POV is re-run on the *unpatched* tree at the new commit first** (`_apply_oracle_revalidation`): one that no longer reproduces there is demoted to `errored`, out of the denominator. That guard is the whole reason a base override is offered at all — nothing else catches it, because `content_fingerprint` hashes the revision the *manifest declares*, not the tree the POV runs against, so a certification stays "valid" no matter which commit is checked out. A benchmark ref that cannot be resolved offline (the project clones are `--depth 1` and carry no tags) reports `unresolved` and keeps the old behaviour rather than guessing; the four known tag peels are checked into `KNOWN_TAG_COMMITS` with their `git ls-remote` evidence, and all four equal our SHA.

### Agents, gates, Docker

- `claude_agents.py` — invokes the `claude` binary per stage, parses stdout (`parse_claude_stdout`, `extract_json_object`), enforces the JSON output schemas in `security_pipeline/schemas/*.json`. Prompts live in `security_pipeline/prompts/*.md`. Three things about `build_command` are load-bearing:
  - **`DISALLOWED_TOOLS`.** `WebSearch`/`WebFetch` are denied because the pipeline redacts the CVE from agents (`to_agent_json_dict`) and an exploiter otherwise searches its way to the advisory *and the official fix commit* — which also contaminates that run's fixPOV score, since those POVs are derived from the same advisory. The rest (`Task`, `ScheduleWakeup`, `Monitor`, `Task*`, `Cron*`, `ToolSearch`, …) are background/orchestration tools that can do nothing useful in a one-shot `-p` agent but were called 20+ times.
  - **`--setting-sources ""` (explicitly empty) + `--strict-mcp-config`.** Agents must inherit no settings but ours. `--settings <file>` only *adds* a source; it does not replace the default set, and with `--setting-sources` omitted the CLI loads all three of user/project/local. So *dropping* the old `--setting-sources user` widened inheritance rather than removing it, and two things came in with it: the launching machine's `~/.claude` settings — including its default **model**, which split the first 30 runs across haiku-4-5 (43 agents) and sonnet-5 (26) — and, because agents run with the worktree as cwd, **the analyzed project's own `.claude/settings.json`**, letting a repository configure the agent auditing it. Verified against claude 2.1.220: a probe settings file in the working tree reaches the agent's Bash env without the flag and not with it. `--model` is pinned anyway (`DEFAULT_AGENT_MODEL`, overridable per run). Note none of this stops `~/.claude/CLAUDE.md`, skills, or plugins from loading — only `--bare` does, and that also kills hooks and OAuth, so it is not usable here.
  - **Z.ai / GLM models (`security_pipeline/zai.py`).** Selecting one of `ZAI_MODELS` — currently `glm-5.1` and `glm-5.2` — in the launcher (or `--model glm-5.3`) routes every agent through Z.ai's Anthropic-compatible endpoint, reading the operator's `~/.claude/settings-zai.json` (override the path with `P2PATCH_ZAI_SETTINGS`). Every `ANTHROPIC_DEFAULT_*_MODEL` slot is retargeted at the selected model — including the haiku one, which Z.ai's stock file points at a cheap "air" model; pinning all three keeps a GLM run single-model instead of splitting the CLI's background turns onto a different one, the same property `--model` being always-pinned gives a Claude run. Three things this deliberately does: (a) it **never touches `~/.claude/settings.json`** — agents run with `--setting-sources ""`, so rewriting the user file would change nothing for the pipeline while silently repointing the operator's own interactive sessions, and it is a process-global mutation while the dashboard runs launches concurrently on possibly-different models; the config is merged into the pipeline-owned `--settings` file and the `claude` subprocess env instead. (b) The **credential never lands in a run artifact**: `agent_io/<agent>/settings.json` is persisted and dashboard-served, so `zai_settings_env` omits `*_TOKEN`/`*_KEY`/… entirely (omitted, not redacted — the CLI applies that file's `env` over the process env, so a placeholder would clobber the real token) and only `zai_process_env` carries it. (c) `zai_process_env` **strips the host's own `ANTHROPIC_*` vars** first, so a machine exporting `ANTHROPIC_API_KEY` for normal Claude use cannot half-authenticate a GLM run. The config-file shape is documented in `README.md` ("Z.ai models"). A missing file, a missing base URL, or an unfilled placeholder key is rejected at launch (`cli.run_command`, `live._validate_options`) rather than surfacing as an opaque auth failure minutes into the first agent.
  - **OpenRouter models (`security_pipeline/openrouter.py`).** Selecting one of `OPENROUTER_MODELS` — currently `deepseek/deepseek-v4-flash`, `openai/gpt-5.6-luna`, `z-ai/glm-5.2` and `z-ai/glm-5.2:floor` — routes the existing Claude Code harness through OpenRouter's Anthropic Messages endpoint (`https://openrouter.ai/api`). The credential comes from `OPENROUTER_API_KEY` or `~/.claude/settings-openrouter.json` (override with `P2PATCH_OPENROUTER_SETTINGS`). Like Z.ai, routing is per-run, all Claude Code model-class aliases plus the subagent slot are pinned to the selected model, host `ANTHROPIC_*` variables are cleared, and credentials exist only in the subprocess environment — never in `agent_io/<agent>/settings.json`. CLI and dashboard launches validate the key before Docker work begins. **`OPENROUTER_MODELS` is an explicit allowlist, not a "contains a slash" heuristic** — a sibling slug like `openai/gpt-5.6-luna-pro` is a different (differently priced) model, so adding one is two edits: the tuple here plus a `MODELS` row in `dashboard/backend/live.py`; everything else (settings env, process env, validation, cost reconciliation) is generic over the tuple. DeepSeek V4 Flash supports only `high` and `xhigh` effort; the launcher default (`high`) is valid for every model on the list. **`z-ai/glm-5.2` and the Z.ai-direct `glm-5.2` are the same model on two routes, and they are deliberately separate launcher rows** — `is_zai_model`/`is_openrouter_model` match on the exact string, so neither claims the other's slug, and only the OpenRouter route can report billed cost. **The GLM 5.2 cheapest launcher arm is provider-pinned.** It keeps the public id `z-ai/glm-5.2:floor` for compatibility, but `openrouter_request_model` sends `z-ai/glm-5.2@preset/autosec-glm52-streamlake`; the workspace-scoped preset documented in `README.md` permits only `streamlake/fp8` and disables fallbacks. This is necessary because Claude Code owns the Anthropic-shaped request body and cannot add OpenRouter's `provider` object. It is now the only `:floor` row; `openrouter_request_model` rewrites that exact id and nothing else, so re-adding a `:floor` arm gives it OpenRouter's normal price sorting rather than this pin. **Never use Claude Code's `total_cost_usd` as OpenRouter billing:** the CLI applies an Anthropic fallback tariff to custom model IDs. OpenRouter invocations therefore retain `stream.jsonl` even without live streaming, deduplicate its structured `gen-*` IDs, query `/api/v1/generation`, and cache the complete sum in `agent_io/<agent>/provider_cost.json`. Cost lookup is observability, not a gate: a partial/failed reconciliation is recorded but cannot fail an agent, and the dashboard uses provider cost only when every generation resolved.
  - **Argv order.** `--disallowed-tools` is variadic: everything after it is consumed as another tool name until the next flag. It must never be the last flag or it eats the trailing prompt and the CLI exits `Input must be provided...`. Same rule for any variadic flag added later.
- `gates.py` — validates agent outputs (`validate_exploiter_output`, `validate_patcher_output`, duplicate-POV-command filtering) before advancing.
- `docker_runner.py` — builds the project image and runs POV/regression commands inside it.
- `workspace.py` — creates an isolated git worktree per run and computes diffs.
- **Project files are not all UTF-8.** Every `subprocess.run(..., text=True)` in the package passes `errors="replace"`. Without it a single Latin-1 file in the diff kills the run: antisamy ships `AntiSamy_*.properties` in Latin-1 (0xFC = `ü`), the patcher edited them to add an error message, and `git diff` output then failed to decode — stranding a run that already had a POV and a patch. The generated `*.diff` artifacts used to be display/LLM-judge only, which made lossy decoding safe; **`fixpov replay` now re-applies `patch_only.diff` with `git apply`**, so a diff has to survive the round trip. Two things follow. (1) **Diff capture must not translate newlines** (`run_local_command(preserve_newlines=True)`, and `write_text` writes with `newline=""`). `text=True` implies universal newlines, which rewrites every CRLF in git's output to LF — measured, 131 CRs dropped from one file's diff — so zip4j (CRLF sources, `core.autocrlf` unset on the run hosts) recorded patches whose context lines matched nothing and `git apply` rejected wholesale. (2) The Latin-1 case is still lossy: `errors="replace"` mangles those bytes, but a mangled patch **fails to apply** rather than reconstructing a wrong tree, and replay falls back to the run's worktree — loud, not silent. Making diffs byte-exact would mean carrying them as bytes end-to-end (they also go into prompts and JSON), which is why it has not been done.
- **A crashed stage still produces a verdict.** `run_alert` catches `Exception`, not just `StageError`, and records a `stage_crashed` step (with traceback) plus a `rejected`/`pipeline` verdict. An escaping exception previously left no `verdict.json` and the run pinned at `created`, which the dashboard reads as still-live.

### Run artifacts (read-only contract)

Each run writes a directory under `security_pipeline_runs/` (gitignored — can be GBs, contains nested git repos, never commit). Key files: `state.json` (step history), `verdict.json` (final verdict + `profile`), `context.json`, plus `git/`, `docker/`, `agent_io/`. **Redaction matters:** `verdict.json` redacts `alert_path` and uses `project.to_agent_json_dict()` so agents/artifacts never see the real CVE; the dashboard maps runs *back* to ground-truth CVEs separately (`dashboard/backend/groundtruth.py`). An `accepted` verdict's `reason` is deliberately worded per-profile so a baseline `accepted` is not misread as objectively verified. **The requested model is recorded too** (`state.json`/`verdict.json` `model`, resolved through `DEFAULT_AGENT_MODEL` so it names a real model): the dashboard's model column otherwise came only from what the Claude CLI reports back per agent (`runs.py:_run_model` over `modelUsage`), which does not exist until an agent finishes — so a queued run, one still building its image, and one whose agents all crashed all rendered as the literal word "default" no matter what was selected. Reported model still wins where present (it resolves an alias like `sonnet` to the concrete id); the recorded one is the fallback, and runs predating the field stay unknown.

### Dashboard

- `dashboard/backend/` (FastAPI) is **read-only** over run artifacts (`runs.py`, `sources.py`, `groundtruth.py`) plus a **live launcher** (`live.py`) that shells out to `python -m security_pipeline run` and streams stages. Live/queue state is **disk-durable**: nothing in memory is load-bearing — `live.recover()` runs on every startup to reattach live runs and reconcile dead ones, so a backend restart is non-destructive.
- **Background run-jobs (`dashboard/backend/run_jobs.py`).** Three buttons re-evaluate one finished run by shelling out to a pipeline CLI command off the request thread: the fixPOV replay (`fix_pov_replay.py` → `fixpov replay`), residual replay (`residual_replay.py` → `respov replay`), and verifier retrofit (`retrofit_job.py` → `retrofit`). The bookkeeping is shared and is where the difficulty lives — an on-disk lock (an in-memory set guarded only one uvicorn worker, so two requests could race over the same run's artifacts), dead-holder reclamation by PID, job-tagged status writes so a late worker cannot stamp its outcome onto a newer job, and a refusal to write status for a run deleted mid-job (which used to resurrect it as a directory of nothing but job bookkeeping). A `JobKind` carries the per-feature differences: bookkeeping file names, eligibility, argv, and which artifact must come back with a newer mtime — a command that exits 0 without refreshing it evaluated nothing. Note `_EXECUTOR_LOCK` is deliberately **not** `_LOCK`: `start` calls `_executor` while holding `_LOCK`, and sharing one non-reentrant lock deadlocked the request thread on the first POST.
- `dashboard/backend/analysis/` holds the LLM judges (patch quality, POV quality, CVE research, reference-patch comparison) used for offline scoring of baseline runs.
- `dashboard/frontend/` is React + Vite + Tailwind + TypeScript.

## Conventions

- Adding a new pipeline capability that changes the flow → add a `Stage` subclass + register it in `STAGE_REGISTRY`, then wire it into a profile. Don't add branching to `pipeline.py`.
- Keep `security_pipeline/` dependency-free (stdlib only).
- Never commit anything under `security_pipeline_runs/` or `Finder Results/` (gitignored generated output). `benchmark/fix_povs/` **is** checked in (curated POVs + manifests); `.fixpov_validate/` (the `fixpov validate` before/after scratch checkouts) is gitignored.
- "Ground truth" now means only one thing: `dashboard/backend/groundtruth.py` maps a run back to its real CVE (the `ground_truth` / `has_ground_truth` fields, `/runs/{id}/ground-truth`). The exploit-coverage evaluator is the fixPOV family (`fix_pov_eval` stage, `benchmark/fix_povs/`, `fix_pov/results.json`, the `fix_pov_eval` field), so the old prefix collision is gone — but it *was* called `ground_truth_eval` / `ground_truth/` before the rename, and readers still accept those legacy names for runs recorded before it. Don't reintroduce the ambiguity by naming anything new "ground truth".
